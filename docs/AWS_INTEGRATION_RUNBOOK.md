## Isolation and permissions

- Use a **separate AWS account**, not merely a new database in the production account. Require independently confirmed production/test IDs in the approval record. The CloudFormation condition is only as correct as the supplied production ID. No resources are created if the account guard fails; do not mistake an empty stack for a successful setup.
- Names derive from one unique `TestName` matching `tickit-it-[a-z0-9-]{3,24}`. Same prefix across foundation, warehouse and runtime stacks. S3 name includes account/region; database is `tickit_it`. Runtime references no production IDs, shared Bronze/Silver paths, workflows, secrets or tables.
- Ingress can read the test bucket, register batches and send FIFO messages; it cannot start Step Functions. Dispatcher can start/describe only the test workflow, inspect test Glue jobs and poll SQL status. Workers can read test versions/coordination state and write their task namespaces; they cannot submit pipelines or execute SQL.
- Controller can invoke only test category/venue functions, submit only four named test jobs and execute SQL/get credentials only on the isolated workgroup ARN. DescribeStatement requires `Resource: *`; it grants status inspection, not SQL execution/results. The separate account is the production isolation boundary for this unsupported resource-scoping API. No service role can assume another role or pass roles.
- DynamoDB CAS transactions require IAM `dynamodb:PutItem`, not a fictitious `dynamodb:TransactWriteItems` IAM action. No worker has DeleteItem. No TTL on coordination/tombstones.
- Bucket policy requires create-only conditional writes and denies deletes on Bronze, manifest, final Silver, pinned input, warehouse and deployment artifact keys. Versioning alone is insufficient. Scratch has separate list/write/delete permissions for Spark's temporary commit files and is never loaded by COPY. Ordinary workers cannot remove the bucket policy or suspend versioning.
- S3 and Redshift must be in the same region. SSE-S3 avoids KMS/presigned URL complexity. No signature-age or network restriction blocks Redshift's one-hour presigned URLs. The COPY role can read only test warehouse manifests/materialized parts.
- No notification or schedule is activated merely by preparing/deploying the templates. The workflow is not started automatically by CloudFormation. Lambda resource policies restrict ingress source bucket/account and watchdog source rule.

## Failure, rollback and cleanup

1. Disable the isolated S3 notification and watchdog rule first, preventing new admissions. Preserve queue/ledger entries and output versions. Never delete a lock to unblock work.
2. If the workflow is active, stop only that isolated execution. SFN stop is **not** child cancellation proof. Inspect registered Glue/SQL IDs; request `batch-stop-job-run`/`cancel-statement` for those exact IDs and poll until actual terminal status. Inspect both branches and outstanding controller invocations. Unknown submissions require service-history/manual reconciliation; do not rerun them or infer that nothing happened.
3. Keep the attempt DRAINING/BLOCKED until the trusted registry is sealed and all external work is proven quiescent. Failure/abandonment requires explicit operator decision/audit reason. Do not automatically release based on TTL, clock expiry, absent receipt or terminal SFN alone.
4. Default-atomic warehouse CALL rolls back staging/dimensions/facts/receipt together on error. A committed receipt means data committed even if the workflow later failed/SNS response was lost; replay is a no-op, not an undo. For this disposable test, preserve evidence then recreate the entire isolated database/environment after quiescence rather than manually deleting SCD2 versions or fact rows. No production rollback is needed because production is untouched.
5. Delete runtime stack after children stop; remove its export dependencies before the warehouse/foundation stacks. Delete manually created usage limit, then warehouse workgroup/namespace/VPC resources (no final snapshot required for synthetic data); verify managed admin secret lifecycle and delete any retained secret/snapshots if explicitly retained.
6. Save receipts/policies/run evidence, remove SNS subscription/queues and foundation stack. Bucket and ledger have Retain/UpdateReplacePolicy Retain: stack deletion does not delete them. After runtime roles are removed and cleanup is authorized, remove the test-only immutable bucket deny policy, enumerate/delete **all object versions and delete markers**, abort remaining uploads, delete the bucket, and manually delete the retained test ledger/PITR backups as applicable. Do not reuse its deleted coordination history for a continuing warehouse.
7. Remove retained Lambda layer versions and Glue custom log groups if stack deletion left any, and inspect test-tag/name resources, SQS/DLQ, managed secrets, snapshots, usage limits and account usage for residual cost. Logs are configured for one-day retention; cleanup should still be prompt. Verify production configuration remains unchanged.

Partial stack failures: leave activation disabled; inspect only test resources. Roll back failed runtime/warehouse stacks in reverse dependency order. Never broaden a policy to a production wildcard to resolve AccessDenied. If dependency/runtime/SQL compatibility fails, stop and return evidence before another billable run.
